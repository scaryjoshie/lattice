## Hierarchy of attention

At project level, worktrees/features dominate. Enter a worktree and the local task
graph and agents become prominent. **Terminals appear when you focus execution**, rather
than being permanently tiled everywhere.

Interaction progression:

```
glance  →  peek  →  enter
```

## Worktrees as visual boxes

Agents live inside worktree boxes that define what they are doing. The box shows the
worktree card (objective, status, tasks, problems, agents, git stats). Agent cards show
`● online / ○ offline`, observed location, and assignment. When location and assignment
disagree, that is visible.

## Semantic zoom / aggregation

Any sufficiently active graph turns into spaghetti without aggregation.

| Zoom | Show |
|------|------|
| Close | `Agent A → Agent B` conversations |
| Broader | `Worktree A ⇄ Worktree B` aggregated relationships |
| Project | Communication nearly disappears; feature dependencies and status dominate |

This also makes future recursive scopes possible without changing the UI paradigm.

## Two views of the same objects

Task DAG on the canvas and task checklist in a panel are both projections of
`Task` + `TaskDependency`. Same for problems, decisions, commits. The canvas is never
the source of truth.

## Modes

Normal mode (direct manipulation) and Ask mode (select + natural language). See
[ask-mode-and-assistants.md](05-ask-mode-and-assistants.md).

## Pane surface: ideas and considerations

Raised during experiment 2, recorded before they are decided. Each notes what it would
cost and what it collides with.

### Panes occupy a grid, not free positions

Today a pane can sit anywhere, and React Flow's dragging is the loose, approximate thing
free positioning always is. Since every pane is the same size (D-50), free positioning
buys nothing: there is no arrangement it allows that a grid does not.

Worth separating two things React Flow does not distinguish:

- **Snapping** is visual. `snapToGrid` / `snapGrid` are built-in props; a pane lands on
  round numbers but the model still stores pixels.
- **Occupancy** is semantic. A pane *is at* a cell, cells hold one pane, dragging
  displaces or swaps. This is a layout model and has to be ours.

Occupancy is the one that makes it feel exact, and it is the one that pays off elsewhere:
grid coordinates make `⌘←` / `⌘→` between neighbours meaningful, make layout two integers
to persist rather than a float pair, and give worktree containers something to align to.
It does not require dropping React Flow — the camera, the node layer and eventual edges
are still wanted. Positions become `(col, row)`, rendered as `col * CELL_W`.

**Settled: a pane is 1x1 and the cell carries the screen's aspect.** A screen is already
wider than it is tall, so a 1x1 pane on an aspect-correct cell *is* the wide rectangle
that "2x1" was reaching for. Spans are the same idea expressed twice, and one of the two
needs no span arithmetic. Multi-cell spans stay available later for a pane that should be
bigger than its neighbours, but must be square in cell count, or the shape stops matching
the screen.

### Empty cells are affordances

A grid has something a free canvas does not: **named nothing**. Every empty cell is a
place where a pane could go, so hovering one can show a `+` and clicking it can offer
Claude, Codex or a shell. Adding a pane stops being a right-click into a void that has to
invent a position, and becomes pointing at where you want the thing. This is a real
argument for the grid on its own, separate from alignment or persistence.

### Worktrees: a region whose card is one of its tiles

The hard part of grouping panes is not drawing the group. It is that a worktree has to
*show* things — objective, branch, counters, tasks — and be clickable, and shading or a
coloured border gives it nowhere to put any of that.

**A worktree occupies one tile of its own region, and that tile is its card.** Agent panes
fill the rest.

This works because it invents nothing. A tile is a thing you click, which scales up into
its full view; that is already true of every pane. So:

```
agent tile       opens into   its terminal
worktree tile    opens into   its tasks, problems, decisions, git
repository tile  opens into   its overview
```

One interaction for everything, and the worktree detail panel stops being a separate
surface that needs designing — it is just what a worktree tile looks like when open.

It also answers a question the first sketch of the pane idea left hanging: what a worktree
with no agents looks like. It looks like its card, alone in its region.

Cost is one tile per worktree. In a 2x3 region that is a card and five agents.

**Sizing.** A region is a rectangle of cells, sized explicitly by dragging its edge rather
than growing to fit its contents. Auto-growth has to displace neighbours, which is the
reflow problem again in a new place. Adding an agent to a full region should grow it
deliberately, as a thing the user did.

**Nesting.** The tree is Repository > Worktree, so regions could nest one level. Not worth
it yet: flatten to worktree regions and leave repository implied until there is a concrete
case for two.

**Shading is reinforcement, not the signal.** A tinted background or a coloured region
border is cheap and helps grouping read at a glance, and it does not conflict with the one
channel rule above, because that rule is about an individual pane's *state* and this is
about *grouping*. It just cannot be the only carrier, for the reason this section starts
with.

**The guardrail.** A labelled region must be a scope — a worktree or a repository — and
not an arbitrary user-drawn group. `core.md` allows exactly one containment hierarchy, and
a second way to put things in boxes is a second tree, whatever the UI calls it. If free
grouping is ever wanted, it needs to enter the model as a real concept first, not arrive
as a canvas feature.

### Two families of tile

Generalising tiles beyond agents — file trees, open files, browsers an agent drives — is
where this gets interesting, and where it could also dissolve into "we built a window
manager". The discipline is that not all tiles are the same kind of thing:

| | Examples | Identity | Lives in |
|---|---|---|---|
| **Subjects** | agent, worktree, repository, integration | Persistent, in the model | The kernel |
| **Views** | file tree, an open file, a diff, a browser | None of their own; a window onto something else | Surface state |

A browser tile is not a peer of an agent tile. It is a *view*, and views are disposable by
nature. Keeping the two apart is what stops the canvas from quietly becoming the source of
truth (V10, D-43): subjects are projected from state, views are just where you are looking.

The test for a new subject type is unchanged — a concrete use case, not a hunch. The test
for a new view type is much weaker, because a view that turns out to be useless costs
nothing to delete.

### Agents never place tiles

The obvious failure of a tiling layout: an agent is boxed in by neighbours and wants to
open a browser. There is no free cell. Anything that resolves this by moving other tiles
means the layout rearranges itself under the person using it, which is the reflow problem
wearing a different hat.

**A tile is a stack, not a single view.** An agent's tile holds its terminal plus whatever
views it opens; the tile shows how many and you page between them. Opening a view is
therefore never a spatial act, and an agent never has to solve a geometry problem it
cannot see.

**Promotion is a human act.** Pulling a view out of a stack into its own cell is something
a person does, when they want two things side by side and can see whether there is room.
Spatial decisions belong to whoever can see the space.

This also lines up with how terminals are actually used. A stack is a tab strip, and
nobody needs it explained.

### What the grid gives away for free

Stable addresses. Every tile is at a cell, every cell has a name, so "this one" and "that
one" become cheap to express — by pointing, by hovering, by speaking, or by an orchestrator
enumerating a layout instead of inferring one. None of that has to be designed in; it falls
out of position being a durable fact rather than a float pair in a browser. It only has to
be *not broken*, which mainly means not moving things without being asked.

### Integration is an event, not a place

The earlier sketch put main on top and feature worktrees physically below it, joined by
edges, so the picture carried "branched from" and "merges back into". On a grid, adjacency
is free, so that reading is gone.

Do not try to get it back. **A pull request is not a place.** What is spatial is where work
is happening; what is temporal is integration. Drawing a merge as geometry means the layout
has to encode lineage, which constrains every unrelated placement decision forever.

Two replacements, both cheaper:

- **Structure is text.** "← main · 3 ahead · 2 behind" on the worktree card is faster to
  read than a line is to trace, and it does not move when someone rearranges tiles.
- **Integration is a tile**, appearing in the worktree's region while it exists: merge
  readiness, divergence, conflicts, the thing you click to act. It is a subject — it has
  state and you act on it — and it disappears with the worktree. V0 already commits to an
  integration experience, so this is not a speculative type.

**Edges are for events, not structure.** A wire lighting up as one agent asks another
something is worth drawing, because it is transient and motion is what the eye catches. A
branch relationship is stable, and a stable relationship is better read than traced. This
is also how the canvas avoids becoming the spaghetti the grid was adopted to escape.

### Repositories are a property of a region, not a container of regions

Two bad options were considered first and both are rejected.

**Nesting** — repository as a box containing worktree boxes containing tiles — is three
levels of rectangle on a 2D grid. Wasteful, and every region becomes a negotiation with
its parent's shape.

**Workspaces** — one repository's grid at a time, switched between like virtual desktops —
removes the nesting but costs something worse. A project spans repositories on purpose
(00-thesis: backend, frontend, SDK). Putting them on separate screens means the
frontend and backend halves of one piece of work can never be seen together, and
cross-repository traffic becomes invisible exactly when it is most worth seeing.

**So repository is not spatial at all.** One project, one grid. Regions are worktrees.
Which repository a region belongs to is a property of that region — its label, its tint —
not its position.

The consequence is the good part: **adjacency then means "related work" instead of "same
repository".** The backend auth worktree can sit beside the frontend auth worktree because
that is the piece of work, which is precisely the thesis. Organising space by repository
would be organising around the wrong noun; 00-thesis is explicit that the durable centre is
the project, not the repository.

Seeing one repository at a time is then a *view*, not a place: highlight or dim by
repository on demand. That costs no geometry and can be a held key.

Nesting drops to one level — region contains tiles — which is the depth the grid handles
well.

### Auto-arrangement is a command, not a daemon

Once position is `(col, row)` and a region is a rectangle, tidying the layout is an
ordinary packing problem, and a good one: it can pack by repository, by activity, by
recency.

It must be **invoked**, never ambient. Anything that rearranges tiles on its own breaks
the one property the grid exists to provide — that where you put something is where it
stays — and it breaks the stable addresses that pointing, speaking and orchestrating all
depend on.

### Future: a shared grid

Deliberately not V0 (08-v0-scope defers teams and collaboration), recorded because it
changes how attractive the grid is.

A grid is far better suited to collaboration than a free canvas. Cells are discrete, so
there is no overlap to reconcile and no pixel-level merge conflict; a region is a
contiguous range of cells, so **ownership is expressible as geometry**. A teammate owns a
region, their agents work in it and you watch it live, and the routing agents in
04-communication become the thing that carries a question from your region to theirs.

Presence on a shared grid is cheap for the same reason: a viewport is a cell range, so
"where someone is looking" is two coordinates rather than a float rectangle.

None of this needs building now. It is worth knowing that the layout model chosen for
single-player reasons is also the one that makes multiplayer tractable, and worth not
designing anything that would preclude it — principally by keeping layout in the daemon
rather than the browser, which is already the plan.

### What a closed pane shows: a card, not a thumbnail

A still of the terminal ("last seen") is **aesthetic, not informative**. At the size a
pane is actually drawn, terminal text is unreadable, so a thumbnail of a screen tells you
nothing you could act on. It is a picture of work rather than a description of it.

So a closed pane should carry legible things: the mark, a title, and later whatever
answers *what is this one doing*. That is the status card the first sketch of this idea
proposed and then talked itself out of.

**This does not cost the zoom.** Opening already scales the box while the contents fade
in; today the contents fade in from nothing, and a card is simply a better nothing. The
box motion carries the continuity, and the content swap is honest, because a card and a
terminal genuinely are different representations rather than two sizes of one thing.

**It softens D-50 without repealing it.** A card has no intrinsic aspect ratio, so the
pane no longer *needs* the screen's shape. But the box should keep it anyway: if the box
changes proportion during the flight, that is the resize look that D-49 removed. Screen
aspect stays, now as a property of the motion rather than of the content.

Stills stay available if a use ever appears — the daemon's mirror and
`serializeAsHTML()` make them nearly free — but they are decoration, and decoration is
not a reason to run a mirror per pane on the client.

### Expressing state without a dot

The status dot was 6px on a thumbnail. Removed.

An earlier version of this section proposed two channels — the mark carrying activity,
the outline carrying attention. **One channel.** Two was over-designed, and the outline
is the wrong half to keep: on a grid, panes are close together and every pane already has
a border, so per-pane outline colour becomes noise exactly when there are enough panes for
it to matter.

The mark carries all of it: pulsing for working, colour for wanting you. It is large,
central, legible at any scale, and it is one thing to reason about rather than a matrix of
two.

### A hover rail instead of a close button

A rail down the right edge, appearing on hover, divided into equal squares. Top square
closes.

**The caution is filling it.** Three slots invented before three actions exist is how a
UI acquires buttons nobody needs, and `core.md` already says to model only what has a
concrete use case. Candidates that are real: restart, fork, open a plain terminal in the
same directory, rename. Until two of those are wanted, a rail that is sized for three and
shows one is better than three buttons where two are decoration.

### Holding Cmd

Extends the parked hold-Cmd surface below. Held on its own, Cmd could show: the open
pane's title (which has nowhere else to live once a pane is open and has no chrome), a
macOS-style switcher across panes, and the available chords drawn as Apple-style keycaps.

**Collision with D-48.** `⌘←` / `⌘→` are already taken: they are start-of-line and
end-of-line for the TUI. Pane switching needs different keys, and macOS supplies the
convention — **`⌘\``** cycles windows within an application. `⌘1`-`⌘9` for direct access
is natural but needs a desktop shell, since browsers keep those for tabs.

### Plain terminal panes

Pane is a terminal manager as much as an agent manager, so a pane that is just `$SHELL`
should exist. It costs one more entry in the provider table and nothing else, and it is
what makes the product coherent rather than agent-only.

### The daemon holds everything; surfaces are disposable

Already true for processes: panes live in the daemon and survive a browser reload.
**Not yet true for layout** — positions live in the browser, so a reload loses the
arrangement. If terminals and display are to be genuinely independent, where a pane sits
belongs to the daemon too. With grid coordinates that is two integers per pane.

Consistent with D-44 (canvas position is a surface concern, stored outside the kernel):
outside the kernel does not mean inside the browser.

## Parked UI ideas

- **3D canvas** with multiple panes where connections between panes are communication
  between worktrees. Probably too much for now, but it maps cleanly onto the
  worktree ⇄ worktree aggregation layer, so it is a natural future projection of the
  same state. Deliberately deferred (see [v0-scope.md](08-v0-scope.md)).
- **Infinite recursion / nesting** of worktrees as nested boxes. Deferred with recursive
  worktrees.
- **Hold-Cmd command surface.** Given D-45, every application command already lives
  behind Cmd. So holding Cmd on its own, without a second key, can reveal what is
  available: the modifier becomes the discovery mechanism instead of a thing you have to
  be taught. Commands are contextual, so the surface is a projection of the current
  selection and mode, like every other surface. Sketch:

  ```
  hold ⌘            overlay fades in over the dimmed canvas
                    ⌘↑   exit pane
                    ⌘⏎   enter selected pane
                    ⌘N   new agent
  release ⌘         overlay fades out, nothing happened
  ⌘ + key           command runs, overlay never appears
  ```

  The overlay must never cost latency: it appears on a delay (~300ms) so a fast
  `⌘↑` never flashes it. Distinct from a command palette (`⌘K`), which is search over
  all commands; this is recall over the ones that apply right now. Deferred until panes
  and the zoom transition work.
